# Architecture

The Rust engine is the single owner of site state. The editor, MCP tools and HTTP clients send operations through one locked Python bridge. They do not keep independent editable copies of the site.

| Layer | Source | Responsibility |
| --- | --- | --- |
| Document model | `native/crates/formweb-model/` | Pages, nodes, styles, components, collections, locales and invariants |
| Commands and history | `native/crates/formweb-engine/` | Atomic changes, revisions, undo and redo |
| Website output | `native/crates/formweb-export/` | Deterministic HTML/CSS/JS output and site checks |
| Process shell | `native/crates/formweb-core/` | JSON-lines request and response transport |
| Service | `backend/app/` | Core supervision, HTTP, project persistence, publication and MCP |
| Editor | `frontend/src/` | Stable DOM shell, selection, inspectors and browser preview |
| Agent skills | `.claude/skills/formweb-harness/` | Ordered website authoring workflows through MCP |
| Agent substrate | `backend/app/substrate.py` | One command surface (catalogue, dispatch, attributed events) behind REST, MCP, `./formweb run` and the terminal; approvals; the external-substrate adapter |
| Live terminal | `backend/app/terminal.py`, `frontend/src/features/terminal.ts` | Pseudo-terminal in the FormWeb folder over a loopback WebSocket, opened only by the FormWeb window, while Agents is on |
| GPU renderer | `native/crates/formweb-render/` | Family wgpu renderer (own workspace and lockfile): area-averaged thumbnails, minimap with a viewport outline, release pixel diffs, a CPU path with identical results, `./formweb render` |
| Desktop shell | `src-tauri/` | Tauri 2 window around the editor on 127.0.0.1:8240; adopts a service there only when its `/api/health` reply names `formweb` and this version, otherwise starts `./formweb serve` (on the first free port from 8241 to 8279 if something else holds 8240) and stops it on exit; one running copy per login (`tauri-plugin-single-instance`), which opens a `.fweb` or `.fpub` handed to it; exposes the renderer as `render_probe`, `render_thumbnail` and `render_diff`; handles every download (the web views save to Downloads without a prompt on all three systems; WebKitGTK picks the folder itself and, with no Downloads entry in `~/.config/user-dirs.dirs`, saves into the working folder, so the shell moves such a file to `~/Downloads`), sends every link that opens a new window to the system browser through `on_new_window` (it loads no shell plugin, whose page script would catch those links first), tells the page where each was saved with a `formweb-download` event and shows the last one in the file manager through `reveal_download`; `./formweb desktop`; builds and runs on Linux with WebKitGTK (see the manual's Desktop shell on Linux) |
| Agent Connect | `frontend/src/features/agent-connect.ts`, `backend/app/clients.py` | MCP switch, client cards, approvals, identity and the attributed activity feed |
| Agent dock | `frontend/src/features/terminal.ts`, `chat-pane.ts`, `backend/app/claude_code.py`, `chat.py` | Session tabs, in-app Claude Code and streamed Chat, both launched with an in-app MCP token |
| Command registry | `frontend/src/commands/`, `backend/app/commands_mirror.py` | One list of commands behind menus, buttons, shortcuts, search and agents |
| Interface languages | `frontend/src/i18n/`, `setup/i18n_check.py` | 26 languages, live switching, lazy tables |
| Vector module | `frontend/src/vector/`, `native/crates/formweb-model/src/vector.rs`, `backend/app/vector_routes.py` | Paths, Live Corners and Illustrator-style tools stored as `svg` and `path` nodes |
| Wishlist | `frontend/src/features/wishlist/`, `native/crates/*/src/wishlist.rs`, export `wishlist.js` | CMS filters, slider, tables, steps, fields and publish checks |
| Frozen desktop engine | `backend/formweb_engine.py`, `setup/freeze_backend`, `./build_app` | PyInstaller bundle of the service, editor and Rust core for the desktop app |

The process shell is `native/target/release/formweb-core` (`.exe` on Windows). `setup/install_core` compiles it. `backend/app/engine.py` serializes access to one process and retains the latest acknowledged state for restart recovery. An unacknowledged request is not reported as successful.

A change follows this sequence: the editor or agent submits commands; Python sends one JSON line to Rust; Rust validates and commits an atomic update; Python persists a history checkpoint and notifies authorized connected editors. The frontend patches existing controls and node representations. The design canvas renders authored data for editing. Preview loads the actual compiler output through a token-scoped opaque iframe, retaining the preceding frame until the replacement loads. Published top-level pages are the final place to verify visitor sessions and consent.

## Contract for new capabilities

Document behavior belongs in Rust. Backend code owns filesystem/network service boundaries. UI code submits operations and renders state; it must not silently repair an invalid document or implement a second command engine. Exported behavior must consume the same stored properties that the inspector edits.

Use stable ids, explicit revision checks for edits based on a read, and atomic batches when a group of changes must undo together. A rejected operation leaves the prior state, revision and history unchanged. Extend MCP using the same service path as the editor, and update the harness workflow if the tool contract changes.

New features are modules at the existing layer seams. Read `frontend/HASHOUT_LOG.md` or `backend/HASHOUT_LOG.md` before editing those layers; for the Rust engine read [[Engine]] and the sidecar's native log. As in formvis and formlit, planning documents, the root log and evidence ship in the planning sidecar, and only the frontend and backend logs stay in the tree.

## Editor layers (v0.6 and v0.7)

**Commands registry.** `frontend/src/commands/registry.ts` holds one `Commands` singleton: each command has an id, label, key bindings (`Mod+Shift+S` form, read from `event.code` so they are layout independent), enabled and checked state, menu, group, description, parameters, and `mutates` and `risky` flags. A duplicate id throws and a duplicate key is dropped from the later command. `keymap.ts` installs one capture listener on the top document; it ignores inputs, textareas, selects, contenteditable and the terminal, so single keys never fire while typing, except commands marked `global` on a Mod combo. Keys pressed while focus is inside the canvas iframe are forwarded by `ui/canvas.ts` to the top document (not from editable targets), so shortcuts work after clicking the canvas. `catalogue.ts` posts the list to the backend, and `backend/app/commands_mirror.py` long-polls the window so MCP `list_ui_commands`, `describe_ui_command` and `run_ui_command` run commands in the open page, with an Allow or Deny prompt for risky ones. User rebinding is stored in `localStorage` only.

**Pages and layers panel (0.29.0).** `ui/context-menu.ts` is the one context menu helper: `showContextMenu(entries, anchor, {host, className, run, returnFocus})` takes items (`id`, `label`, `enabled`, `title`, `keys`, `run`) and `{separator: true}` entries, anchors at a pointer position or an element, and handles arrow keys, Home, End, Enter, Escape and outside clicks; `menuKeyPressed` and `anchorOf` serve the Menu key and Shift+F10. The layers menu (`fw-layer-menu`) and the page menu (`fw-page-menu`) are built with it. `features/panel/` holds the panel logic: `index.ts` (`installPanel`, the page and layer commands and menus, row keyboard wiring) and `pages.ts` (free copy name and slug, list moves as `page.move` commands, the home page batch). Page commands take an optional `id` so a menu can act on a page other than the open one; `invoke(id, params)` runs a registered command for such a target. `rename.ts` puts a fixed field over a row's label in the overlay root (rows are buttons and the lists are `keyed()`, so the field cannot live inside either); the row only hides its label, so nothing moves. `fold.ts` owns folding: `LayerFolds.rows()` is the layers walk (it skips paint definitions and `tspan` as before, leaves out the children of folded rows, and counts every layer for the heading), folded ids are kept per page in memory and in `localStorage` (`formweb.layers.folded`, at most 64 pages and 2,000 ids each) and the heading state in `formweb.panel.sections`; nothing goes into the site, because FormPublisher opens `.fweb` files with an older engine. A change of selection unfolds its ancestors once, so folding the parent of the selected element keeps it folded. The twisty sits in its own grid column, reserved on leaf rows, and is placed by `grid-column` so the rows' child order is unchanged. `drop.ts` is the pure drop logic and takes lists of ids, for the canvas drag and multi-select that build on it: `zoneAt(fraction, into)` (thirds over containers, halves elsewhere), `dropTarget(site, root, ids, over, zone, open)` returning `{over, zone, parent, anchor}` or null (no page roots, no drop into the dragged nodes or their descendants, only `CONTAINER_TAGS` take children, nothing in or out of linked instance structure, as `guard_structure` in the engine refuses), and `moveCommands(site, ids, target)`, which turns the move into `node.move` commands in document order against a simulated child list and leaves out no-ops, so one drop is one batch and one undo step. `pages.ts` has the same shape for pages (`pageMoveCommands(site, ids, anchor)` as `page.move` commands). `drag.ts` is the pointer controller for both lists: a 4 px threshold so a click still selects at once, a fixed drop line in the overlay root, the `is-drop-into` outline, auto-scroll within 28 px of the list edges, Escape to cancel, and the click after a drop swallowed. Row clicks go through `pageRowClick` and `layerRowClick` in `main.ts`, which pass the event on and do not stop modifier clicks.

**Multi-select (0.30.0).** `features/selection.ts` holds the selection in memory only (nothing reaches the site or the .fweb file). `selectedId` in `main.ts` stays the primary element, so all single-selection code is unchanged; the module keeps an ordered list of further ids next to it and collapses to the primary whenever something else changes `selectedId`, and the same for pages, where the primary is the open page. Readers: `selectedIds()` (always holds the primary, empty until the engine is connected), `primaryId()`, `isSelected(id)`, `isMulti()`, `topMost(ids)` (drops page roots and any id inside another listed id, in document order: the nodes an action should change) and `selectedPageIds()` (site order). Writers: `selectNodes(ids, primary)` and `selectPages(ids, primary)`. Import them from `./features/selection` in `main.ts` (or `../selection` from `features/panel/`). `installSelection(host)` wires the keys on both lists (Ctrl or Cmd+A, Escape, Shift+Up and Shift+Down); `layerClick`, `pageClick` and `canvasClick` are the click rules (Ctrl or Cmd toggles and makes the toggled item primary, Shift takes the visible range from the anchor, a plain click selects one), called from `layerRowClick`, `pageRowClick` and the canvas `onSelect`, which now receives the click event. Rows get `aria-selected` on every selected item and `is-multi` on the ones besides the primary (`styles/selection.css`, tokens only); the canvas marks them with `data-fw-marked`, a dashed outline next to the primary's solid one, set through `Canvas.mark(ids)` before each render and never part of the export. `features/selection-actions.ts` builds the actions on the set, each one `/api/batch` (one undo step): duplicate (`node.duplicate` per top-most node, then selects the copies), delete (`node.remove`), copy and cut (one `/api/fragment` per node, written to the clipboard as `{format: "com.nodemode.formweb.fragments", version: 1, items}`), paste (`/api/paste` with `fragments`, which the service checks fragment by fragment, refuses past 8,000 nodes in all (from 0.31.0), four times the 2,000 of one fragment, and runs as one `node.paste` batch; the editor's multi copy refuses the same total before it writes the clipboard), move up and down (`dropTarget` and `moveCommands` per parent, as a block), the layer drag ids (`dragIds`) and the page set (`pageSetFor`, `duplicatePages`, `stepPagesCommands`, `deleteSelectedPages`). The existing commands (`edit.copy`, `edit.cut`, `edit.paste`, `edit.duplicate`, `edit.delete`, `arrange.up`, `arrange.down`, `page.duplicate`, `page.move-up`, `page.move-down`, `page.delete`) branch to these when more than one item is selected, so there are no parallel command ids. Nodes a guard refuses (page roots, linked instance structure) are skipped and counted in the status line. The inspector keeps editing the primary; its identity reads "3 elements selected" and the tag line names the primary.

**Interface languages.** `frontend/src/i18n/` holds the translator, `langs.ts` (26 codes, English the source), `keys.ts` (the ordered English strings) and `locales/*`, plus the formvis family tables in `family/` copied unchanged. Later layers win: family tables, then FormWeb's own locale. A MutationObserver translates text nodes and title, aria-label and placeholder by exact English match before paint, remembering the English so switching never needs a reload. Content, layer and page names, the terminal, the chat log and the canvas iframes are never translated. Each language loads lazily; see [[Languages]].

**Quick insert flyout.** `frontend/src/features/panel/insert-flyout.ts` (styles beside it) is the popup behind the Layers plus button and the `insert.quick` command. It mounts once into `#overlay-root`, hidden, and every open only refills its groups with `keyed()`, so nothing is rebuilt; filtering toggles `hidden` on rows and groups, and the list keeps the height it had unfiltered so the popup never resizes while typing. It is positioned from the anchor's rectangle (below, or above when that side has more room). Focus stays in the filter and the highlighted row is exposed with `aria-activedescendant`. The module knows no site data: `main.ts` hands it the groups (the Insert panel's `INSERT_ELEMENTS`, `SECTIONS` and the site's components) with each item's run function, which is the Insert panel's own `insertElement`, `insertSection` or `insertComponent`, so both surfaces insert identically.

**Canvas frame and scripts.** `ui/canvas.ts` draws the page into an iframe whose `srcdoc` starts with a `Content-Security-Policy` meta (`default-src 'none'`, images, media and fonts by URL, inline styles, `form-action 'none'`) and is sandboxed with `allow-same-origin allow-scripts`. `allow-scripts` is there for WebKit only: WebKit (Safari, and WebKitGTK in the Linux desktop app) runs no event listener at all in a frame sandboxed without scripts, not even the listeners the editor attaches from the parent, so clicks, double-clicks, right-clicks, drags and keys on the canvas would do nothing; Chrome runs them either way and prints a warning that a frame with both flags can escape its sandbox. With both flags the frame shares the editor's origin, so a script that ran in it could drive the editor, and three rules keep any from running. First, the renderer builds every node with `createElement` and `textContent` from allowlists that match the engine's: no `script`, `style`, `iframe`, `object`, `embed`, `meta`, `base`, `link`, `foreignObject`, `animate` or `set` element, no `on*`, `style`, `srcdoc`, `action` or `formaction` attribute, `href`, `src` and `poster` only as http(s), `mailto:`, `tel:` or relative URLs, styles one property at a time through `style.setProperty` with `url(`, `expression` and `@import` refused, and no `innerHTML` anywhere; code sections never reach the canvas (it shows their poster image or a placeholder) and run only in the compiled preview frames, which are sandboxed without `allow-same-origin`. Second, the policy blocks inline, external and `data:` scripts, event handler attributes, `javascript:` URLs, `eval` and plugins, and a second policy meta can only narrow it. Third, the frame never leaves its first document, because a page loaded into it later would carry no policy and keep both flags (a published page under `/published/` or `/sites/` runs its code sections on the editor's origin): links on the canvas keep their address in `data-fw-href` and have no `href`, so no click, middle click, link drag or "Open Link" item of the browser's own menu can load a page in the frame; forms are refused by `form-action 'none'`, by the sandbox (no `allow-forms`) and by the parent's `submit` listener; and `bindEvents` cancels every `navigate` event of the frame's window through the Navigation API (Chrome, and WebKitGTK 2.52), which also stops a link that a future renderer change might let through. Keep all three when changing the canvas; the link underline that `href` gave comes from `a[data-fw-href]` in the canvas stylesheet.

**Canvas context menu.** `frontend/src/features/canvas-menu.ts` builds the right-click menu of the design canvas with `showContextMenu` into `#overlay-root` and registers its own commands (`edit.text`, `edit.select-parent`, `edit.wrap`, `style.copy`, `style.paste` and the `inspector.*` field shortcuts); every other item runs the existing command, so the menu, the menubar and agents share one path. No site script runs in the canvas iframe, so the module attaches `contextmenu`, `keydown` (Menu key, Shift+F10), `pointerdown` and `scroll` listeners from the parent to the iframe's document once `Canvas.loaded()` resolves, and `ui/canvas.ts` is unchanged. A pointer position inside the frame is converted to the parent document with the frame's rectangle and its scale (`rect.width / offsetWidth`, since the frame is scaled to fit the stage); the keyboard form anchors at the selected element's bottom left, clamped to the visible part of the stage. Edit text dispatches a `dblclick` on the element so the canvas's own inline editing runs. Right-click is left to the browser while any canvas text is being edited. Wrap in container is one batch (`node.add` of an empty div, `node.move` of the div to the element's index, `node.move` of the element into it), offered only when the parent can hold elements and is not linked instance structure (`canContain` from `features/panel/drop.ts`). Copy styles keeps the picked breakpoint's style map in memory; Paste styles sends one `node.update` per selected element in one batch, with `null` for styles the copy lacks. The module reads the selection from `features/selection.ts` through its host (`selectionIds`, `topMost` and `selectNodes`, wired in `main.ts` as for the canvas drag): right-clicking an element that is already selected keeps the selection and makes that element the primary, so Edit text, Rename and the field shortcuts address the element under the pointer, and the labels carry counts through `countLabel` from `features/selection-actions.ts`, as the layers menu does. Wrap in container moves the selected siblings of the primary, in their order, into the new div.

**Canvas drag.** `frontend/src/features/canvas-drag.ts` (styles in `styles/canvas-drag.css`) moves elements by dragging them on the canvas; `main.ts` only calls `installCanvasDrag` with the canvas frame, the stage, the overlay root and the `selectedIds` getter of `features/selection.ts`, so pressing any selected element drags the top-most selected elements as one set and the selection is kept after the drop. `ui/canvas.ts` is unchanged: no site script runs in the iframe, and the module attaches a `pointerdown` listener to its document once `canvas.loaded()` resolves, plus one `style` element in its head that only sets the grabbing cursor, `user-select: none` while `html[data-fw-dragging]` is set, and the dimming of `[data-fw-drag-source]`, none of which changes layout or reaches the export (the exporter works from the engine). A press on a selected element, outside an inline text edit and without modifier keys, arms the drag; it starts after 6 px, so click and double-click are untouched, and the click after a drop or an Escape is swallowed. Move, up and cancel listeners go on both the canvas document and the top document, and the pressed element takes pointer capture, so the drag survives leaving the frame. `FrameMap` converts between top-document and canvas coordinates from the frame's rectangle and `offsetWidth` (the scale the canvas fit applied), and the canvas's own viewport coordinates already include its scroll, so every scale and scroll offset maps correctly; the visible area is the frame clipped by the stage. `findDrop` hit-tests the canvas document, reads the parent's computed `display`, `flex-direction`, `grid-auto-flow` and column tracks to decide whether siblings flow in rows or columns, and picks before or after by the nearer half along that axis; over a container it uses a 12 px edge band for before or after the container itself and otherwise the nearest child slot inside it, or "into" when it is empty. Every candidate goes through `dropTarget` and `moveCommands` from `features/panel/drop.ts`, so the canvas and the Layers list share one set of rules; an invalid candidate walks up to the next ancestor (pointing into a linked instance lands beside the instance), and a no-op shows nothing. The proxy, the insertion line and the container outline are fixed elements mounted once in `#overlay-root` and only toggled with `hidden`. Within 40 px of the top or bottom of the visible canvas the canvas document scrolls (then the stage). A drop is one `/api/batch` of `node.move` commands, so one undo step.

**Touch, pen and Select several.** `features/hold.ts` holds what both drags share for touch: a 350 ms hold with an 8 px slop, `startsDrag` (left button only, and for a pen only `buttons === 1`, so the barrel or eraser button never starts a drag), a permanent non-passive `touchmove` listener on the list and on the canvas document that calls `preventDefault` only while a drag is armed (setting `touch-action` after `touchstart` does not affect the running gesture, so this is what keeps the list or canvas still), a capture `contextmenu` blocker on the top window and the canvas window for the length of a held gesture, and a synthetic `contextmenu` at the release point when a hold ends without moving, so the existing menus open by touch on every platform, including those that never fire `contextmenu` on a long press. `installRowDrag` and `installCanvasDrag` keep the mouse path as it was (4 px and 6 px thresholds, immediate) and run pens through it; a touch press arms a timer instead, and moving past the slop first gives the gesture back to the browser, so it scrolls. When the hold takes, the row gets `is-lifted` or the element `data-fw-lifted` (on the canvas an unselected element is selected first), the drag then follows the finger with pointer capture, and listeners filter by `pointerId`: a `pointerdown` of any other pointer or a `pointercancel` ends it with no command. A touch lift outside the list or the canvas finds no target. `features/select-mode.ts` adds the header toggles (one shared state, `picking()` in `features/selection.ts`, which makes `layerClick`, `pageClick` and `canvasClick` toggle as Ctrl+click does), the count and Done bar laid over the heading's first grid column so nothing moves, the `edit.select-mode` command, Escape on the window, and a capture `dblclick` blocker on the lists and the canvas window while the mode is on; `main.ts` repaints it from `update()`.

**Vector module.** `frontend/src/vector/` draws and edits on an overlay above the canvas. The model is plain engine data: an `svg` node holding `path` nodes, with `d` always the rendered result and `data-fw-vector` the anchor model (including Live Corners, which stay non-destructive). One gesture is one engine batch, so undo, revision and MCP behave as for any edit. The tag and attribute allowlist, the `d` grammar and same-svg `url(#id)` references are enforced independently in `formweb-model/src/vector.rs`, `ui/canvas.ts` and `backend/app/assets.py`, which must stay in step. `POST /api/vector/import-svg` cleans imported SVG with the same rules. Tool letters are handled by the vector editor's own capture listener, which runs before the keymap.

**Wishlist runtime.** The creative features live in the model, engine and export crates as `wishlist.rs`, with a small `wishlist.js` runtime in exports for published-list filters, sorting, sliders and multi-step forms. The editor side is `frontend/src/features/wishlist/` (one panel, nine tabs, every edit an ordinary engine batch). Form file uploads and validation presets are checked in `backend/app/forms.py`.

**Bringing a node into view.** `Canvas.reveal(id)` in `ui/canvas.ts` scrolls the canvas document (never the editor) so the node sits in the middle of the part of the frame the stage shows, or its top when it is taller, and sets `data-fw-reveal` for two seconds: the canvas stylesheet pulses `outline-offset` on top of the selection outline (a static wider offset under reduced motion), so layout and export are untouched. `Canvas.bring(id)` scrolls only when the node is outside that part, to the nearest edge. Audit Select uses `reveal`, scrolls the layer row with `scrollNearest()` from `ui/reveal.ts` and writes "Selected {0}: {1}" to the status line; a page issue whose code has a field (`seo.title`, `seo.description`, `seo.base-url` and `seo.base-url-404` to the Base URL, `page.address-case` to the URL slug) opens the Page inspector, scrolls that field to the middle of the panel and flashes it (`flash()`, class `fw-flash`). Since 0.31.1 Select also puts the same sentence in the shared `Notice` (error style, so it stays 30 seconds) with a Show again action that clicks the row's Select button again while the keyed row still holds the same issue key; the middle position keeps the field clear of the notice in the bottom right corner. Layer rows and crumbs call `bring` through `pickNode()`; a click on the canvas only selects and never scrolls. The crumbs are `features/crumbs.ts`: the path takes the free width of the stage header (`flex: 1 1 0`, so its content never moves the width note or the readout), and `fit()` (on every update and from a `ResizeObserver`) hides middle crumbs nearest the page first, then the page crumb, behind one "..." crumb that opens the hidden ones through `ui/context-menu.ts` as raw (untranslated) names; only then does the current crumb shrink, to no less than 5em, with an ellipsis.

**Page background.** The site model has no site-wide background field (the site background below is a token): a page's background is the `background` style of its root node, and `page.add` gives a new root none. The exported stylesheet sets no body color, so such a page is white with black text in a browser, and the canvas document (`ui/canvas.ts`) draws the same defaults (`color-scheme: light`, `Canvas` and `CanvasText`) so the editor shows what visitors get. `frontend/src/features/inspector/page-background.ts` builds the Page tab's Page background group and the commands `page.background`, `page.background-clear`, `page.background-all` and `window.theme-colors`; every change is an ordinary `node.update` on the page root's base styles, and Apply to all pages is one batch, so one undo step. Before either writes, `backgroundRefusal` resolves the site's tokens in the value and asks `CSS.supports('background', ...)`; a value the browser does not parse is refused with a status message. Match another page (0.31.1) is a select filled by `matchChoices()` (the home page, the page at / or else the first, comes first) through `options()`, so it updates in place; a pick runs `page.background-from {from}`, one `node.update` built by `matchPatch()` that copies the other page's `background` and `color` and drops a local `background-color`; `page.background-home` is the same with the home page. The Add page dialog's Background select is filled by `startChoices()`; for a page choice `startCommands()` gives the `node.update` for a root id the editor makes up, sent in one batch after `page.add {id, root}`, so the new page and its background are one undo step. These copy values; nothing links one page's background to another's.

**Site background.** The link between pages is a design token, not a model field, so `.fweb` files stay readable by older engines (FormPublisher's among them) that refuse unknown fields: the site background is the token `--page-background` (stored as `page-background`, a valid token identifier), and a page is on it when its root's `background` is exactly `var(--page-background)`. The exporter already writes every token into `:root` and the other theme's values into `html[data-theme]`, and the canvas already sets the site tokens on its document, so the canvas and the export agree with no Rust change. `page-background.ts` derives everything from the site: `siteBackgroundKey`, `backgroundMode` (site, own), `siteBackgroundPages`, and `pageColorToken`, which offers the token the home page's background already uses (or one named `paper`, `bg`, `background`) on a site without `--page-background`; adopting it stores `page-background: var(--paper)` and `siteBackgroundTarget` then edits `--paper`, so there is one colour. The group's three choices are radio inputs; Same as another page and This page only only change which part shows until a value is written. `useSiteBackgroundCommands` sends `token.set` (the first time) and every page's `node.update` in one batch. The other theme's value is written by `otherThemeValueCommand` from `inspector/theme.ts`, the helper the Themes block uses. `startCommands` gives a new page `var(--page-background)` when the token exists. `readableTextPatch` (contrast from `features/contrast.ts`) adds `color: #ffffff` to a root with no text colour when its new background needs light text, and removes exactly that value when a light background follows, inside the same `node.update`. Nothing runs on load. Commands: `page.background-site {color?}`, `page.background-site-all`, `page.background-site-color {color, theme?}`, `page.background-site-theme`.
**Inspector search.** `frontend/src/features/inspector/search.ts` indexes the mounted inspector instead of keeping a field list: every `.inspector-section` (its `data-section` id and title) in the four tab panes, and in each the `.field`, `.checkbox-field` and direct buttons with their visible label, the CSS property from `data-style` or `data-field` (attribute fields carry `data-attr`) and the synonym groups in `search-terms.ts`. Anything under a `hidden` ancestor is left out, so a control the inspector hides for the selection never shows; a disabled control is listed as unavailable. A MutationObserver on the panes only marks the index stale; it is rebuilt on the next keystroke or, while results are open, once per frame. The list is a `keyed()` list in a sibling of `.inspector-scroll`; the two swap with `hidden`, so the panes keep their state and scroll position. The command is `inspector.search`.

**Frozen desktop engine.** `./build_app` builds the editor and Rust core, freezes `backend/formweb_engine.py` with PyInstaller (`setup/freeze_backend`, `requirements_desktop.txt`) and runs the Tauri build. Inside the bundle (`config.FROZEN`) the core binary and editor come from the bundle and data lives in `~/FormWeb` (or `FORMWEB_HOME`); `formweb_engine.py --selfcheck` names anything missing, and the Tauri shell spawns the frozen engine as a sidecar.

## Family services

Some capabilities belong to a sibling app, and FormWeb calls it rather than copying it. Background removal (`backend/app/background.py`) sends an uploaded picture to formvis's engine (`FORMWEB_FORMVIS_URL`, default `http://127.0.0.1:8190`, `POST /api/ops/remove-background`) and gets a soft mask back. Everything else stays in FormWeb: the editor's brush refinement, compositing with Pillow, the new asset and the one-step `node.update`. When formvis is not running, the feature reports how to start it and nothing else is affected.

Stock photos (`backend/app/stock.py`) work the same way with formlit. FormWeb searches formlit's catalog with its `library.query` and `photo.get` commands (`FORMWEB_FORMLIT_URL`, default `http://127.0.0.1:8390`). It proxies thumbnails so the browser never talks to formlit, and on insert saves formlit's developed preview as an asset carrying the photo's IPTC rights. Bundled icons need no sibling. SVG assets exist only for them: `assets.clean_svg` rebuilds every SVG from an element and attribute allowlist (no colon allowed in any value), uploads stay raster-only, and SVG responses carry a sandboxing CSP. Asset metadata may hold a `license`, which `.fweb` files carry and exports list in `CREDITS.txt`.

Image generation (`backend/app/imagegen.py`) also belongs to formvis. FormWeb lists formvis's generators (`GET /api/generate`): local models need no key, and cloud ones use the person's keys, kept in formvis. It starts a job (`POST /api/generate`) and follows it (`GET /api/jobs/{id}`). When the job finishes, it copies each picture into its assets with provenance (prompt, generator, licence, time) and asks formvis to forget its copy. Editing goes the other way through formvis's MCP endpoint. `open_file` puts the picture in the formvis window, which asks the person once to allow outside agents, and `export_image` returns the edited document as the element's new picture in one `node.update`.

Writing (`backend/app/writer.py`) uses the family's one language-model setting, kept in formvis. That is any OpenAI-compatible chat service: Ollama or LM Studio on the computer, or a hosted one with the person's key. FormWeb posts to formvis's `POST /api/llm/chat` with no tools; the key stays in formvis.
- **Copy:** returns suggestions only. The editor applies a suggestion after review with one `node.update`.
- **Site outline:** a site plan is JSON that `validate()` clamps to at most 4 pages, 6 sections per page and 4 items per section, with section kinds from a fixed list, links limited to `/`, `#` or http(s), and text lengths capped. Slugs are resolved against the existing pages before the person sees the outline.
- **Small models (v0.5.7):** when a model cannot write the outline as JSON, `plan()` drafts in guided mode: FormWeb lays out the pages and asks one short question per text ("About the website: ... Task: ..."), cleaning each answer and falling back to plain text when the model echoes the description. Copy marks a suggestion `unchanged` when the model hands the text or the request back. Every model call runs in a worker thread, so the editor stays responsive while a local model writes; access checks stay on the event loop.
- **References and revision (v0.5.7):** `reference()` reads a PDF's text with pypdf (at most 20 pages, 6,000 characters) or an image's main colours with Pillow, and keeps no copy. Text goes to the model as facts; colours go into the outline's `palette`, used for the accent when the site has no readable brand or library colour. Revising sends the current outline and the person's instruction; a failed revision leaves the outline as it was.
- **Build:** `build_commands()` turns the plan into one engine batch. `page.add` takes caller-chosen `id` and `root` so the same batch can fill the root, and the batch is capped at the engine's 500-command limit. Each page gets exactly one `h1`, with the first section heading promoted when there is no hero. The button accent is the most saturated brand or library colour that reaches 3:1 contrast on the section, else orange, with text colour chosen from its luminance.
