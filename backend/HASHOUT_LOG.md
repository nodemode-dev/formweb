# Backend context

## A site import counts only what it keeps, refuses a project's source, and takes loose HTML files · v0.32.0 (2026-11-26)

The first of five releases (0.32.0 to 0.36.0) that answer the follow-up on issue #36; `frontend/HASHOUT_LOG.md`, same version, has the editor side. The routes, the review and answer shapes and the `mode` and `revision` parameters are unchanged.

Counting (`app/site_import.py`): `MAX_ENTRIES` (1,000) now counts only kept entries, after `__MACOSX`, `node_modules` and dot folders are dropped (`_ignored`, the old rule factored out with `_parts`), and is checked after `zipfile` has parsed the list. The hard bound before parsing is the end record's count against `MAX_RAW_ENTRIES` (40,000) and the 2 MiB `MAX_LISTING` cap, and a third check (`len(infos)`) runs after parsing for zip64 archives. Why 40,000: a central directory record is at least 46 bytes plus its name, so 2 MiB can describe at most about 44,600 entries even with one-letter names; with realistic dependency paths of 60 to 80 characters the 2 MiB cap binds first, at roughly 15,000 to 18,000 entries. `zipfile` parsed 40,000 entries in about 0.1 s. The 12-level depth check now runs after the ignore check, so it applies only to kept entries: dependency trees are routinely deeper than 12 levels, ignored entries are never opened, and leaving the check first would have refused such a zip for the wrong reason, as the old count did. The limit is still 12, and a 20-deep kept path is still refused. The refusals for count and size now say what to do and end with "Nothing was imported."

Source projects: `_project(names, files)` refuses (status 400) a zip with a `package.json` at the top or one folder down, outside ignored folders (that folder is the project folder), that also meets one of these: no `.html` or `.htm` file outside ignored folders; a `.ts`, `.tsx`, `.jsx`, `.vue` or `.svelte` file (`BUILD_SCRIPTS`) anywhere under the project folder's `src/` (`src/main.ts`, `app/src/App.jsx`); or, with the pages read, a kept page that loads a local script ending in one of those extensions, a kept page holding `%PUBLIC_URL%`, or a kept page that loads a local `type="module"` script importing a package by name (`_bare`: an `import ... from "x"`, `import "x"` or `export ... from "x"` line whose specifier does not start with `.` or `/` and has no `:`, so URLs do not count) while no kept page has a `<script type="importmap">`. Why the bare import is a rule and not a gap: a browser cannot run such a module without an import map, so a finished site cannot depend on one. The layouts this catches beyond the first version (found in review): a `public/index.html` with `%PUBLIC_URL%` and `src/*.js`, a `src/index.html` beside `src/main.ts`, and a plain-JS app whose `index.html` loads `/src/main.js` with bare imports. It runs after the archive is read, so a static site with a harmless `package.json`, plain `.js` with relative or URL imports, or a `src/` of `.js`, `.css` or pictures imports, with `package.json` skipped. The sentence names its reason (scripts that still need building, placeholders a build fills in, scripts that load packages by name, or no HTML page) with up to three examples. A `dist/index.html` or `build/index.html` (`BUILT`), at the top or one folder down, adds a sentence naming that folder. When the archive is refused for count or size before the pages can be read, names alone decide: besides the name rules above, a `.tsx`, `.jsx`, `.vue` or `.svelte` file anywhere, or a `.ts` file under any folder named `src`, counts, so the `.ts` segments of a video stream elsewhere do not; the source sentence then replaces the count or size sentence (status 413). For archives refused before `zipfile` opens them, `_peek` reads the names from the central directory with `struct`, record by record; it only chooses the sentence and never accepts anything. It stops at the first bad signature, after 200,000 records read (`MAX_PEEK`) or 16 MiB of list scanned (`PEEK_BYTES`), decodes a name only when its bytes end in `package.json`, `.html`, `.htm` or a build extension, and keeps at most 100 names of each of those kinds (`PEEK_KEEP`); a 62 MB crafted list answered in about 0.3 s through the route.

Loose files (`app/library_routes.py`, `site_import.loose` and `read_files`): both site import routes also take `{"files": [{"name", "html"}]}` when the content type is `application/json`; `_archive` returns the bytes or the decoded JSON and `_read` sends each to `read_archive` or `read_files`. `read_files` returns exactly the structure `read_archive` gives for a zip holding those files at its top level, so `plan`, `commands`, undo and the revision check are shared, and the review of the loose form equalled the review of the same files zipped, byte for byte, for text the service received intact. That parity also needs the editor to decode a picked file as the service decodes a page inside a zip (`_text`: UTF-8, then Windows-1252); it read files with `File.text()`, UTF-8 only, until review found that Windows-1252 pages lost their accented letters, and now decodes them the same way (`frontend/HASHOUT_LOG.md`). Each name is cut to its base name after backslashes become slashes (`../x.html` is `x.html`); a name that is empty, longer than 255 characters, unprintable or starts with a dot is refused (a zip would silently ignore a dot file); only `.html` and `.htm` are taken; duplicates are compared after NFC and case folding, as in a zip; 1 to 100 files (`MAX_PAGES`); an `html` text with a lone surrogate, which `json.loads` accepts and UTF-8 cannot encode, is refused with 400 and a sentence asking to save the file as UTF-8 (before review it raised an unhandled error, a 500); the 128 MiB total check in `read_files` cannot be reached, because the body is capped at 64 MiB like a zip (by the request guard in `main.py` for a declared length, with its general sentence, and by `_archive` for a chunked body); a page over 1 MiB is skipped with the reason a zip entry gets, not refused. A body that is not JSON, including 200,000 nested brackets, gives a 400 (`RecursionError` is caught). The access record's `bytes` is the sum of the page bodies for loose files. The MCP tool `library_import_site` still sends bytes, so it changes only through `read_archive`; its description now states the new limits and the source refusal.

Fixes after the feature run (same version): every refusal `read_archive` and `read_files` can raise now ends with "Nothing was imported.", and several were reworded to that end (a link, a path outside the folder, an archive that is not a zip, a password, an archive over 64 MiB, which now also says what to do). The two inner errors of the asset check are caught and become skip reasons, not refusals, so they were left as they were, and `commands()` refusals are outside both readers. No test quotes the old wording. The page warnings for outside files now read "{n} external scripts are not brought along: {list}." and "{n} external stylesheets in the page head are not brought along: {list}." (with a singular form for one). The editor has its own 64 MiB sentence for a file too large to send, in `site-import.ts`, which is not a service sentence.

Still open: the request guard in `app/main.py` answers a declared Content-Length over 64 MiB with its generic sentence before `_archive` runs, so the new 64 MiB sentence appears only for a chunked body without a length. Checked by HTTP against a running engine with synthetic archives (1,200 entries with 800 in `node_modules`, 15,000 short `node_modules` entries, a 16-deep `node_modules` path, 5,000-entry and small source projects with and without `dist` or `build`, 1,501 real files, a claimed 65,535 entries, a 5.7 MB file list, 41,000 entries, and the loose-file cases); every refusal left the revision unchanged. `pytest tests/site_import tests/hostile`: 222 passed before and after. Not tried: a real installed dependency tree, and the MCP tool.

## Local publications run apart from the editor, addresses ignore capitals, and the site import fixes · v0.31.1 (2026-11-25)

Part of the final pull request for issue #36 (`frontend/HASHOUT_LOG.md`, same version, has the editor side and how the branch was stacked; `.docs/wiki/Publishing.md` has the full design). The 0.31.0 known gap said a locally published site should only be one you trust; this closes it.

Sandbox: every answer under `/published/` and `/sites/` carries `Content-Security-Policy: sandbox allow-scripts allow-forms allow-popups allow-popups-to-escape-sandbox allow-modals allow-downloads` (`LocalAccess` in `app/main.py`) unless the route set a stricter one, the same class of policy as `/preview/<token>/`. Without `allow-same-origin` the page has an opaque origin and its requests send `Origin: null`. Such an origin may read only a release's `assets/` files, its `search-index.json`, its `site.webmanifest` and its form endpoint, answered with `Access-Control-Allow-Origin: null` and never credentials, because any sandboxed frame on any website also has an opaque origin. Uploaded and clipboard assets answer with `sandbox`, and the page password form runs no script and posts with the service's own origin.

Runtime token: `Studio.publish` makes `secrets.token_urlsafe(32)` per publication and stores only its sha256 (`release_runtime`). The exporter writes the token only into each page's `fw-config` context (`native/HASHOUT_LOG.md`), never into `runtime.js`, the search index or the manifest. `runtime.js` calls `/api/runtime/~{token}/...` on the page's own origin with `credentials: 'omit'`; `LocalAccess` looks the token up, rewrites the path so the token is not logged, and `runtime_site` refuses it for another publication. Visitor and consent tokens are bound to the token's digest and travel in headers, never cookies. A page's own GET and HEAD reads of its release folder carry `X-FormWeb-Runtime`; those answers are `Cache-Control: private, no-store` with `Vary: Origin, X-FormWeb-Runtime`, so a cached answer never reaches a frame without the token. Member sessions live in page memory: following a link inside the release trades the session for a single-use ticket (two minutes, sha256 stored) in `?fw-member=`, which the next page uses up; a reload or a new tab starts signed out.

Gated files: an asset is protected when every page that uses it sits behind a password or a member gate; it is answered to someone who unlocked one of those pages or through `/_fw/{key}/assets/...`, an HMAC key over slug, version, page id and a 12 hour expiry that `serve_release` writes into the links of a protected page it has just served to someone allowed. The search index is filtered once, at serving time, for every release including older ones, and Publish passes the site's `passwordRoutes` to the export so new indexes leave those pages out too. `site.formweb.json` is no longer written into a local publication and older publications refuse it; it stays in the exported ZIP as the editable source.

Addresses: the service refuses an address another page holds in other capitals for add, update, duplicate and bulk create, and a site zip page whose address clashes that way gets another address instead of failing the import. Site import: a stylesheet `url()` already rewritten to an asset is not checked again (it was reported missing), and an outside `@import` such as a web font moves to the top of the page's CSS, where browsers read it.

Tests: `backend/tests` has 513 tests at the release (security, export, pages and site import cases for all of the above).

## A static site comes in from a zip, and a paste takes several fragments · v0.31.0 (2026-11-25)

Part of the issue #36 work, shipped as 0.28.1, 0.29.0, 0.30.0 and 0.31.0; this entry records the service side of all four (`frontend/HASHOUT_LOG.md`, same version, has the editor side and the release split). The fragments list of `/api/paste` shipped in 0.30.0; the site import, its second-round fixes, the paste total, `expected_revision`, the editor page revalidation and the tests ship in 0.31.0.

`app/site_import.py` (new) · reads a site zip in memory and plans it as pages, assets and skipped files. The archive is untrusted: its end-of-archive record is checked (at most 1,000 entries, a 2 MiB file list) before `zipfile` parses anything (corrected 2026-11-26, v0.32.0: the end record is now checked against 40,000 entries and the 2 MiB list, and the 1,000 limit counts only entries outside ignored folders, after parsing; see the v0.32.0 entry above), then the caps on pages, folder depth, unpacked size, per-type asset size, links, passwords, paths outside the archive and suspicious expansion apply; system files are ignored and a single top folder is stripped. Each HTML file becomes a page with one code section: the body as HTML, `<style>` blocks and local stylesheets as CSS (`@import` and `url()` followed), and the first script, local or inline; later scripts, the page head and other font formats than WOFF2 are left out with a note. Script handling is never looser than Import HTML: both use the shared `kit_script` helper in `library_routes.py` (the Import HTML shim was refactored into one function for this). Names that differ only by Unicode normalisation (NFC, case-folded) are refused as duplicates, as names differing by case already were. A mislabelled picture and a reference to a skipped file are reported in plain words.

Stylesheet imports (second round): `css()` follows a local `@import` with the set of stylesheets already on its path, so a loop is cut at the `@import` that closes it, each stylesheet arrives once, and the review names the loop in one sentence (`site.loops`). Imports are followed `IMPORT_DEPTH` 4 levels deep; a stylesheet past that is named (`site.deep`), as is the one that takes a page past the 256 KiB `CSS_CAP` (`site.overflow`; that page is skipped), and the local `@import` rules that were not followed are stripped, so no bare local `@import` is left in the section's CSS to fail later. Outside `@import`s stay as written.

Scripts that are not JavaScript (second round): `script_type()` reads a script element's `type` and returns it unless it is a JavaScript type, and both importers use it, `site_import.py` for each page and `library_routes.py` for Import HTML, so JSON-LD, JSON, import maps and templates are never taken as the section's script. `left_out_scripts()` is the one sentence both paths give for them.

`app/library_routes.py` · `POST /api/library/import-site/review` and `POST /api/library/import-site`, both capped at 64 MiB by the request guard in `app/main.py` (`SITE_ARCHIVE_PATHS`), and both read and plan off the event loop (`asyncio.to_thread`). Import re-sends the same bytes with the reviewed revision, so the server stores nothing between the two calls and a site changed since the review is refused. The import is one batch, one undo step. "Safe to replace" (`canReplace`) means no extension entry or component source outside the page's own code sections names a node in the page, so a site imported before can be imported again over itself.

Review found and fixed a denial of service: fan-out `@import`s and repeated `<link>`s multiplied stylesheets past 3 GB, and unclosed tags made the patterns scan for over 30 s. The patterns now scan once, each stylesheet is inlined once per page within the 256 KiB styles cap, and outside files are one warning.

MCP `library_import_site` (`app/authoring_tools.py`, `app/mcp_server.py`) · review (default) changes nothing; import adds pages (mode new) or swaps matching routes (mode replace). Approval is decided per call: only mode replace asks, and its approval card shows the zip's size, action and mode instead of the first 1,000 characters of base64. It takes the review's revision as `expected_revision`, like its neighbours; the older name `revision` is still accepted and `expected_revision` wins when both are given. The tool table and counts in the docs say 17 authoring tools and 104 in all.

`app/fragment_routes.py` · `/api/paste` accepts `fragments` (up to 64), checks each as before and pastes them in order as one `node.paste` batch, one undo step; the editor uses it for pasting several copied elements. One paste of several fragments brings at most `MAX_TOTAL_NODES`, four times the per-fragment limit, 8,000 nodes in all, refused with one plain sentence before anything is pasted. The single-fragment path the MCP tool uses is unchanged.

`app/main.py` · the editor page (`index.html`, and every `.html` of the built editor) is served with `Cache-Control: no-cache`, so it is revalidated on every load and the desktop app never keeps showing an older editor after an update; the other built files keep no cache header, as before.

Tests: `backend/tests/site_import` (pages, addresses, links, SEO and assets as one undo step, hostile archives refused or bounded with the site unchanged, the loop and depth rules, `expected_revision`, single-page Import HTML and the site import treating scripts alike), `paste` (fragments in order as one undo step, the 8,000 total), `pages` (an address in use refused), `export` (the `site-export.zip` contract FormPublisher reads), `images` (audit and export agree on alt text) and `hostile` (no route makes a script, frame, handler, style or script URL node). The three defects the site import tests found (the loop, the depth, JSON-LD) were fixed and their expected-failure marks removed. `pytest backend/tests`: 451 passed.

## The engine has a lock, a log, a watch on its app and a way to be started alone · after v0.24.0 (2026-11-19)

The family's Windows start pattern (FormTools 0.10.0), engine side. Up to here `formweb_engine.py` had no lock on the data folder, no log file and nothing that ended it when the app went, so an engine could be left running after a quit and a failed start left nothing to read.

`app/startup.py` is FormTools's `backend/app/core/startup.py` unchanged except the five names at its top (`APP`, `NAMES`, `SHELL_ENV` `FORMWEB_SHELL_PID`, `ALONE_ENV` `FORMWEB_NO_SHELL`, `ERRORS_NAME`). It keeps FormTools's double quotes because it is a copy. FormWeb has no `core` folder, so it sits in `app`. `PLACES` was left as it is: FormWeb's engine is one file beside the app's program in all three install layouts (the Windows install folder, `FormWeb.app/Contents/MacOS`, `/usr/bin`), which is the `.` entry.

`app/runtime.py` is new and small: `start_logging(data)` opens `<data folder>/logs/formweb-engine.log` (1 MiB, three older files kept) on the loggers `formweb`, `uvicorn` and `uvicorn.access`, and a second call for the same file puts the same handler back where it was taken off; `claim` and `release` are the lock (`<data folder>/engine.lock`) with one log line when a leftover engine was ended.

`formweb_engine.py` · `--selfcheck` is decided first and is unchanged, except that it now imports `app.main` itself, which the top of the file did before. `serve()` then goes in the family's order: the data folder and the log (a folder that cannot be made is one sentence and exit code 5), `keep_errors` (an absent standard error goes to `logs/formweb-engine-errors.log`), the started-alone branch (a frozen engine with no `FORMWEB_SHELL_PID` and no `FORMWEB_NO_SHELL=1` opens the app beside it and exits 0, or says "formweb-engine is a part of FormWeb and serves nothing on its own. Open FormWeb instead." and exits 4; no lock, no port), the lock (refused: the sentence in the log and on standard error, exit code 2), the watch on the app's process, then the window key line and the server as before. The app is imported only after the lock is held, so a refused engine starts no Rust engine of its own. `uvicorn.run` became `uvicorn.Server(uvicorn.Config(...)).run()` with the same arguments so the log handler can be put back after uvicorn's log setup, which removes it from the `uvicorn` loggers. `main()` writes an error that ends the engine to the log before it is raised.

An ordinary stop: uvicorn shuts down in order on a terminate signal and then raises the signal again, which ended the process before the lock was given up (seen: exit 143, the lock still there). ## The engine starts with no standard streams · v0.23.1 (2026-11-19)

## Runtime boundary

`app/engine.py` supervises one Rust JSON-lines subprocess with one asyncio lock. Standard output carries protocol replies only. Core stderr is drained into the Python logger. Requests use increasing IDs and a 30-second acknowledgement timeout. Engine failures leave the last acknowledged site cached for restart recovery; an interrupted request fails visibly rather than being silently replayed. Revision conflict engine errors map to HTTP 409.

`app/service.py` serializes mutating operations and project/publication actions through an action lock. Rust owns the site and history. The Python service persists acknowledged autosaves in SQLite and restores the last site at startup. Undo history is process-local and is not serialized into `.fweb` files. New/imported sites clear the current saved-project identity. Existing projects are reopened by their stored site and subsequent save updates that project.

`app/store.py` uses the local ignored `backend/data` directory for SQLite, native files, export ZIPs and immutable publication snapshots. WAL is enabled. `.fweb` files carry `{format:"com.nodemode.formweb",version:1,site}`. Native saved files are atomically replaced; publication versions are new directories and never overwritten. Export paths reject absolute paths, traversal, backslashes, drive separators and null bytes.

### Checkpoint and project durability

The native checkpoint is `{schemaVersion:1,site,revision,undo,redo}`. Every acknowledged operation captures a complete validated Rust checkpoint. Startup and subprocess crash recovery restore the exact last acknowledged revision and complete history. Explicit project opening restores history while advancing the active revision. Invalid checkpoint documents and cross-site history are rejected atomically by Rust.

Main project mutations automatically update that named project's SQLite site/checkpoint without changing its display name. Active branch mutations automatically update only that branch snapshot and checkpoint. Switching projects or branches therefore retains acknowledged edits and undo/redo without requiring a second Save. Explicit Save also writes the portable `.fweb` file; current and project-ID download endpoints generate the latest corresponding acknowledged document/checkpoint. The on-disk path returned by explicit Save remains that explicit portable snapshot until the next explicit Save.

Portable native files now include the complete checkpoint and the union of owned raster assets referenced by current, undo and redo documents. This prevents undo from restoring a missing image after import into a fresh runtime data directory. Native envelopes and HTTP/MCP transport bodies are bounded at 64 MiB, history at 100 entries per direction and 32 MiB, current native sites at 8 MiB, individual rasters at 8 MiB and embedded asset count at 500. Legacy envelopes without checkpoint or assets remain accepted. Extra images restored before an invalid model rejection can remain as inert local digest files; the active model is unchanged.

Deleting a project requires management permission, removes its saved document/checkpoint, branches, branch checkpoints, comments, presence and grants. Frozen published versions and attributed historical activity remain independent release/audit records. If a named owner deletes the active project, its identity owns the fresh workspace; other identities receive no implicit access to it.

### Collaboration and attribution

Configured `FORMWEB_AUTH_TOKEN` is required before editor identities can be created. With authentication unconfigured, the local owner mode cannot claim enforced separate user roles. If identities already exist and root authentication is removed, dropping Authorization fails closed. Identity bearer tokens are revealed once and stored only as hashes. Browser control API/SSE cookies are random per identity, HttpOnly, SameSite Strict, process-bound and expire after twelve hours. MCP always requires the corresponding bearer identity and ignores browser cookies.

Roles are `viewer`, `reviewer`, `editor`, `publisher` and `owner`, with read/comment/review/edit/publish/manage permissions. The same service checks guard HTTP and official SDK tool/resource operations. Each MCP callback derives its actor from `ServerRequestContext.request.headers`; it does not inherit the manager's startup ContextVar identity. Presence lasts one minute unless refreshed. Comments retain the authored node ID through reorder and serialize author identity/name. Activity records accepted operations with the same REST/MCP actor.

Branches store base/current branch snapshots separately from main. Saving an open branch never overwrites main. Review requires main to be open and returns changes, current revision and conflicts with escaped JSON pointers. Dictionaries merge recursively; differing arrays are atomic conflicts. Merges require explicit `current` or `branch` choices for every conflict and can require `expectedRevision`; Rust records the merged site as one undo entry. Revision conflicts return HTTP 409 or an MCP execution error with status 409. A caller can read the fresh state and explicitly retry; no conflicting mutation is silently replayed.

SSE queues carry the affected project ID, coalesce slow subscribers and recheck current authentication/project permission before delivering state or keepalive. Revoked access emits an access-denied event and closes the stream. Browser cookies authenticate SSE without putting bearer tokens into query strings.

### Forms, inbox and delivery

Frozen publication and immutable preview forms validate their own saved document, not a later draft. Public default form endpoints are usable by visitors; a form reachable only through gated pages requires a matching visitor membership. Editor bearer identities do not substitute for website visitor identities. A shared form reachable from a public page remains public.

`extensions.forms.forms` configures success/error messages, success redirect, tracking query fields and per-field constraints. Intake returns field-specific `errors` with HTTP 422; typed outputs include finite numbers, checkbox booleans and bounded multiple-choice arrays. Required flags, email, URL, ISO dates, numeric bounds/step, radio/select choices, repeated-field cardinality, min/max lengths and a restricted regular-expression subset are checked. Patterns exclude groups, alternation, backreferences and more than one unbounded quantifier. Files are unsupported. Bodies are bounded at 64 KiB, field count at 128, values at 4096 characters, and IP requests at twelve per minute; the honeypot rejects automated entries before storage.

Inbox and CSV reads filter by permitted site IDs. CSV prefixes formula-like cells and carries typed values and declared tracking fields. Retention is persisted per site or for the root owner's global policy, applies at startup and every minute, and removes submission metadata plus corresponding durable delivery jobs and attempts. An already-initiated outbound network request cannot be recalled by deletion.

Webhook configuration contains approved endpoint URLs and `secretEnv` references, never inline secrets. `FORMWEB_WEBHOOK_HOSTS` is an exact host allowlist; production transport requires HTTPS/TLS on port 443, pins the approved resolved address and preserves hostname TLS validation. Explicit `FORMWEB_ALLOW_LOCAL_WEBHOOKS=1` exists only for loopback diagnostics. `FORMWEB_WEBHOOK_SECRET` is an example signing reference. Jobs survive restart, deduplicate submission/endpoint pairs, retain bounded attempt history and retry at most eight times with capped backoff. Terminal client errors exclude retryable 408/429. Signatures cover timestamp, job ID and the exact JSON body. Accepted locally stored submissions report queued or unavailable delivery honestly; no email delivery is claimed.

- refers-to: `app/window_key.py`, `app/main.py` :: LocalAccess, window_key_claim, window_ticket, `formweb_engine.py`
- kind: security
- logged: v0.22.0 · 2026-11-19

The engine makes one key per launch (memory only). LocalAccess, the one guard, refuses with 403 any write on a control path (`/api/*`, `/mcp`) when the caller is the root identity (no token, or `FORMWEB_AUTH_TOKEN`) and does not send `X-FormWeb-Window-Key`, and refuses window-only paths (`/api/agents*`, `/api/approvals/settings`, `/api/terminal*`, `/api/chat*`, `/api/window/ticket`) to every caller without it, named bearer identities included. A named identity's other writes stay governed by its role. The open list is `/mcp` (outside agents, with the Agents switch and approvals) and `/api/window/key`; site visitor routes (forms, runtime, password forms, the commerce webhook, `/published`, `/sites`, `/preview`) are not control paths and stay as they were. GET `/api/approvals` and `/api/terminal/sessions` need the key from root too. With `FORMWEB_WINDOW_KEY_STDOUT=1` (the desktop shell's sidecar) the engine prints `formweb-window-key: <key>` flushed before uvicorn starts and the bootstrap route answers 404; otherwise `/api/window/key` answers once and then 409. `./formweb serve` runs uvicorn directly, so a shell that starts it, or adopts a running engine, leaves the page on the bootstrap.

Sweep of `app.openapi()` write operations with no key: 86 of 86 answered before; after, 88 operations (two new), 75 refused, 13 answered (the bootstrap and the visitor routes above).

### app/substrate.py :: Approvals.decide, settings; app/seal.py

- refers-to: `app/substrate.py` :: Approvals.decide, Approvals.settings, Approvals.update_settings, `app/seal.py`
- kind: security
- logged: v0.22.0 · 2026-11-19

A decision is refused on the agent or terminal channel, from the root identity without the key, and from the same identity on the same channel that asked (release reviews keep their own rule). The stored approval setting carries an HMAC-SHA256 seal keyed by a 32-byte value in the system keychain (`keyring`, service FormWeb, account settings-seal, imported lazily). A record whose seal is missing or wrong while `agentDestructive` is off reads as on, with `seal: "broken"` and `sealBroken: true`; with no keychain the values stand and `seal` is `"unavailable"`. A deleted record reads as the product default (off): the default is the loose value, so the seal catches edits, not removal.

### app/main.py :: LocalAccess, a refusal to a window origin carries the CORS headers

- refers-to: `app/main.py` :: LocalAccess, `tests/test_window_key.py` :: test_a_refusal_carries_the_cors_headers_for_a_window_origin_only
- kind: fix
- logged: v0.22.0 · 2026-11-19

`LocalAccess` is the outermost middleware (it is added after `CORSMiddleware`), so a refusal it sends itself (the missing window key, a wrong or missing server token, the body size limit) never passed through the CORS layer. The development editor on 5240 or 5241 talks to the engine on another origin, so the browser hid the refusal behind a CORS error and the page could not read the 403 or 401 text, for example to ask for the server access token. Seen in headless Chrome against an engine started with `FORMWEB_AUTH_TOKEN`, the editor on another port: every call was blocked by CORS with `net::ERR_FAILED`; after the change the same calls answer 401 and the page reads it. Only an origin in `ORIGINS` gets `access-control-allow-origin` (the origin itself, never `*`), `access-control-allow-credentials: true` and `vary: Origin`; a foreign origin, `null` and a request with no origin get none, as before. The packaged window is same-origin and never needed it. The headers go on every refusal made for an allowed origin, including the 421 for a wrong Host, which tells that origin nothing it could not learn by asking.

### ../setup/agents.py, ../agents/manifest.json: the app writes down what it offers agents

- refers-to: `../setup/agents.py` :: manifest_text, mcp, skills, manifest_sync, sync_all, `../agents/manifest.json`, `tests/test_agents_manifest.py`
- kind: feature
- logged: v0.22.0 · 2026-11-18

`./formweb agents sync` also writes `agents/manifest.json` (format `form-agent-manifest`, version 1, the shape formadaptor's `spec/agent-manifest.schema.json` defines) and `--check` exits 1 printing `agents: drifted agents/manifest.json` when the committed file is not what sync would write. Why: the family spec, the gateway and the skills installer read these counts from one file the app writes about itself instead of carrying typed numbers.

Where each field comes from. `app` is `formweb`, the file name of `apps/formweb.json` in formcompiler (declared in the script). `mcp.tools` and `mcp.read_only` are read from `app.mcp_server.TOOLS`, the list `tools/list` sends, in its order: 103 tools, 37 whose `readOnlyHint` is true; compared with a running engine (`tools/list` on port 29400, window key header): same 103 names in the same order and the same 37. `mcp.transports` is `stdio` when `setup/mcp_stdio.py` exists and `http` when the MCP app has a `/mcp` route. `skills` is read from `.claude/skills`: `formweb-editing` and `formweb-skillset` with no sub-skills, `formweb-harness` with 18 (the director and 17 specialists). `extensions` is null: FormWeb hosts no form.ext extensions. The script imports the backend registry with `FORMWEB_DATA_DIR` set to a scratch folder and without byte-code, so a sync leaves nothing in the data folder or the tree; it needs the backend's packages, which CI has when it runs the check.

`mcp.approval_gated` is the tools that wait for a person today under the default settings, and under the defaults that is one: `run_ui_command` (a command the editor marks risky shows an Allow box in the window for 45 seconds; the gate is `runFromBridge` in `frontend/src/commands/catalogue.ts`, reached through `commands_mirror.run`; it does not depend on any setting). The other gate, "Ask me before an agent deletes...", is `agentDestructive` in the approval settings and is off by default (`seal.effective` reads a missing value as false, so a project that never saved the choice, or whose record was deleted, is off; a record that was edited by hand while the keychain seal is intact reads as on). With it on, `call_tool` in `mcp_server.py` waits up to 100 seconds in Agent Connect for every tool that declares `destructiveHint` (15 today: `edit_nodes`, `edit_pages`, `edit_styles`, `edit_cms`, `edit_site`, `edit_creative`, `open_project`, `load_project_file`, `delete_project`, `set_form_retention`, `motion_remove`, `motion_track`, `variables_remove`, `library_apply_preset`, `new_site`), but for the domain tools and `motion_track` only when the one command removes something (a `.remove` command, `site.replace`, a null motion track), and for `apply_commands` only when a batch holds a `.remove` or `.delete` command. The script reads the default through `seal.effective` with the keychain switched off, so changing the default in `seal.py` and running sync adds those tools (and `apply_commands`) to the manifest on its own. Declared in the script: `WINDOW_GATED` (`run_ui_command`) and `REMOVE_GATED` (`apply_commands`), because their gates are code in the engine and the window, not data; sync stops with an error if either name leaves the registry. `publishReview` (also off by default) does not wait: `promote_release` answers `pendingApproval` and a reviewer approves later, so it is not in the field.

`dock` is declared in the script, because the page's code cannot be read for it reliably: the dock is the bottom terminal and agent dock (`TerminalDock` in `frontend/src/features/terminal.ts`, mounted under the stage in `main.ts`; `Kind` there is `shell`, `claude`, `chat`), it has no other position, and its tabs are those three kinds. The truth lives in that file; change `DOCK` when the dock moves or gains a tab.

Run: sync wrote the file; formadaptor's `scripts/manifest.py check agents/manifest.json --app formweb` accepted it; `--check` exited 0. In a copy of the repo outside the tree, renaming `list_projects` and then turning `audit_site` read-only off each made `--check` exit 1 naming `agents/manifest.json`. With a running engine: default settings, `new_site` ran at once; with the setting on, the same call waited and Agent Connect's list showed it pending (the call was cut after 6 seconds by the client). Tests: `test_the_committed_agent_manifest_is_current` and `test_the_manifest_lists_what_tools_list_returns`, written after the runs above. No document stated a different count: the wiki already says 103 tools.

### app/substrate.py :: Approvals, a waiting agent call says what a dialog needs, and windows are told when it comes and goes

- refers-to: `app/substrate.py` :: OFFERS, ALWAYS, EVENT, Approvals._row, Approvals.wait, Approvals.decide, `app/service.py` :: Notice, Studio.announce, `app/main.py` :: events, `app/mcp_server.py` :: caller, CLIENT_HEADER, `app/claude_code.py` :: NAMES, tab_name, issue, revoke, `app/chat.py` :: _run
- kind: feature
- logged: v0.22.0 · 2026-11-19

Preparation for the family's shared dock (its engine contract, clause 15), additive: the present window reads none of this and keeps polling `GET /api/approvals?status=pending` as before.

A row of kind `agent.tool` in `GET /api/approvals` and in the answer of `POST /api/approvals/{id}` gains `agent` (the name the caller gave: the `x-formweb-client` header, else the product word of its `user-agent`, else empty; for FormWeb's own tabs the tab's name, `Claude Code` or `Chat`), `inApp` (true for FormWeb's own tabs), `what` (`run <tool>`, to finish "It asked to ..."), `offers` (`["deny", "once"]`), `always` (`"all"`) and `expires` (milliseconds since the epoch while the call waits, null afterward). `agent` and `inApp` are also kept in the row's `subject`, so they survive in the stored record. A `release.promote` row gains nothing: a release review is not an outside-agent question.

Why `offers` has no `always`: the existing `approve` already is "once" (it lets that one call run and the next destructive call asks again, seen below), and a standing yes in FormWeb is the sealed owner setting `agentDestructive`, which a reviewer who may approve a call may not change. `always` says what that setting covers (every agent, FormWeb's own tabs included) for the day an owner-only answer is added.

`GET /api/events` gains a second event name, `approval`, beside `state`: `{"type":"request","id"}` when a call starts to wait and `{"type":"withdrawn","id","reason"}` with reason `approved`, `denied` or `expired` when it stops. It carries the id only, on purpose: the event stream is read without the window key (an `EventSource` cannot send it), and what is waiting is a read that needs the key, so the window fetches the row. The MCP endpoint runs stateless, so the client name of `initialize` is not there at call time; that is why the name comes from a header.

Run on port 28473 with a fresh data folder, as an outside agent through `/mcp` with Agents on and the setting ticked: the pending row carried the fields above and `expires` 100 s ahead; a decision without the window key was refused; deny gave the agent "The person denied delete_project"; approve let that call through to the tool and the next call waited again; a call left alone ended after 100.0 s with the 408 sentence; a call whose client hung up after 3 s stayed pending (the server does not notice) and expired at its own 100 s. The event stream showed `request` for each and `withdrawn` with `denied`, `approved` and `expired` twice. Also seen: the approval settings are kept per site id, so after an approved `new_site` the new site was back on the default and the next call did not wait.

### app/service.py :: Studio.set_agent_access, a stored Blocked stops every agent, FormWeb's own tabs included

- refers-to: `app/service.py` :: ACCESS_META, BLOCKED, DOCK_CONTRACT, Studio.agents_enabled, Studio.agents_blocked, Studio.agent_access, Studio.set_agent_access, Studio.start, `app/seal.py` :: access_mark, access_sign, access_effective, `app/main.py` :: LocalAccess, agents, AgentAccess, agent_access, agent_access_set
- kind: feature
- logged: v0.22.0 · 2026-11-19

The family contract (clause 15) has a standing choice `blocked` that refuses every agent, the app's own Chat and agent tabs included. FormWeb had nothing like it: Agents off is the default, is not stored, and lets FormWeb's own Claude Code and Chat through on purpose (the dock never needed the switch). Making Agents off refuse FormWeb's own tabs would have changed what the present window does for everyone who never touched the switch, so Blocked is a separate choice a person makes, and nothing changes until they make it.

`POST /api/agents/access {choice}` with `blocked`, `ask` or `allowed` (manage role, window key: it is under `/api/agents`). `blocked` writes the meta record `agentAccess` (`{choice: "blocked", seal}`), turns the Agents switch off and closes the terminal sessions the editor did not open, as the switch does. From then `/mcp` answers 403 "Agents are blocked in FormWeb. Only a person in the FormWeb window can change that." to every caller, an in-app tab token included, and it still does after a restart. A plain shell tab opens as before; an agent tab can still be opened, its tool calls are refused. `ask` and `allowed` remove the record, turn the switch on and set `agentDestructive` (true for `ask`) through the existing sealed setting; like the switch they last until the engine stops. `GET /api/agents/access` (read permission, no key) answers `{choice, stored, agentsEnabled, agentDestructive, ownTabs, seal, sealBroken, contract}`: `choice` is `blocked`, `ask`, `allowed`, or `off` for the state FormWeb starts in (outside agents refused, own tabs working), which has no word in the contract and is the owner's to name. `contract` is the dock contract version this engine implements (clause 16). The old `POST /api/agents {enabled: true}` removes a stored Blocked, so the switch in the present window never shows on while everything is refused.

The record is marked with the keychain seal. Any record that is present reads as blocked; one whose mark does not verify reads as blocked with `sealBroken: true`. A record deleted outside the app cannot be told from one never written, and falls back to the switch, which starts off. The defaults are untouched: Agents off, `agentDestructive` false.

Run on port 28473 with a stand-in keyring: at start `choice: off`; a Claude Code tab's token read the site with Agents off, as today; the set route without the key 403, with a wrong word 422; after `blocked` the same tab token and an outside caller both got the 403 sentence, a shell tab opened, and `GET /api/system` said `agentsEnabled: false`; after a restart still blocked; with the stored record edited by hand, still blocked and `sealBroken: true`; the old switch on gave `choice: ask` and `stored: null`; `allowed` let a destructive call through unasked and `ask` ticked the setting the present page reads.

### app/agent_programs.py: agent status in one call, Codex and Cursor as tab kinds, and a close route

- refers-to: `app/agent_programs.py` :: PROGRAMS, find, version, signed_in, status, cursor_config, launch, `app/main.py` :: agent_status, `app/terminal.py` :: Open, open_session, Close, close_session, listing, `app/claude_code.py` :: ENTRY, NOT_INSTALLED, INSTALL_LINE, issue_env, mcp_config, _base, require_cli, `app/chat.py` :: _events, `tests/test_dock_engine.py`
- kind: feature
- logged: v0.22.0 · 2026-11-19

Preparation for the shared dock (contract clauses 3, 6, 10, 11, 13, 14, 16), additive: the present page keeps `/api/claude/status`, `/api/agents/clients`, the presets that type `codex` or `cursor-agent` into a shell, and closing through the socket.

`GET /api/agents/status` (read permission) answers `{claude, codex, cursor, tabs, contract}`; each program is `{installed, version, install, signedIn, path, title}`. `install` is a command line and is empty when the program is found. `version` is the first line of `<program> --version`, run once per program file and kept until the file's modification time changes, so a second call took 0.02 s. A program that is not on the engine's PATH is looked for through the login shell at most once a minute. `signedIn` is true when the program's own sign-in file is there (`~/.claude/.credentials.json` or `CLAUDE_CODE_OAUTH_TOKEN` for Claude Code, `~/.codex/auth.json` for Codex, honouring `CLAUDE_CONFIG_DIR` and `CODEX_HOME`) and null otherwise, never false: on macOS Claude Code keeps its sign-in in the keychain, and Cursor's place is not known to the engine. `tabs` is the dock tabs this caller may open (all five for the manage role where a pseudo-terminal exists, none otherwise; the programs are then left out and nothing is run). The engine never calls this itself.

`POST /api/terminal/open` takes `kind: codex` and `kind: cursor`. The program starts in FormWeb's agent folder (the one Claude Code uses) with an in-app token of its own in `FORMWEB_INAPP_TOKEN`; the token is never an argument and a shell tab has none. Codex is given the server on its command line as configuration overrides that name the variable (`mcp_servers.formweb_tab.url` and `mcp_servers.formweb_tab.env_http_headers`), so nothing of the person's Codex settings is written. Cursor reads `.cursor/mcp.json` of its working folder, so the engine keeps an entry `formweb_tab` there, mode 0600, whose header value is `${env:FORMWEB_INAPP_TOKEN}`; other entries in that file are kept and a file that is not JSON is left alone. A missing program answers 424 with "is not installed" in the sentence and `code: "notInstalled"` plus `install`; the Claude Code refusal gains the same two fields beside its unchanged sentence. The token ends when the tab ends, as for Claude Code.

The entry the engine writes for its own tabs is now `formweb_tab` for Claude Code and Chat too (it was `formweb`), with `--allowedTools mcp__formweb_tab`, so it cannot be confused with the `formweb` entry of a project file that starts `./formweb mcp`. Chat strips the new prefix from tool names, so the Chat pane shows the same names as before.

`POST /api/terminal/close {id}` (manage role, window key) ends a session and answers `{id, closed}`; `closed` is false for an id that is already gone, and the call never fails for that. `GET /api/terminal/sessions` rows gain `alive: true` (a session that ended is not listed). A socket that is attached when the session is closed this way receives the typed `exit` frame it always did.

Run on port 28473 with stand-in programs named `claude`, `codex` and `cursor-agent` first on the engine's PATH, its own HOME and a shell that reads no profile. With them: all three found with their version lines; each kind opened a tab; the stand-ins saw the arguments above and, for Codex and Cursor, the token in the environment; `ps -eo args` held no token; the shell tab's environment held none; each token read the site through `/mcp`; a destructive call with the Codex token waited as `agent: Codex, inApp: true`; after close each token was refused 403 with Agents off, and with Agents on the same token counted for nothing (the call was treated as any outside caller and waited for a person); the Claude Code config file was gone. Without them: `installed: false` with the install lines, and 424 for each kind. The present page's calls were replayed and answered as before, including the socket with a one-time ticket (ready, replay, input, resize) and a reused Claude Code tab. Write routes walked without the key: 74 of 74 refused before, 76 of 76 after (the two new ones are `/api/agents/access` and `/api/terminal/close`).

Not verified: the real Codex and the real Cursor agent were not available, so whether Codex accepts the two overrides and whether Cursor expands `${env:...}` in a header is taken from their documentation as remembered, not from a run. No restart route was added; the contract lets an engine leave it out.
