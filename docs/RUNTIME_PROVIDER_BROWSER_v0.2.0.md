# Runtime provider browser verification · v0.2.0

Twenty-two checks passed on 2026-10-10 in a separately launched Chromium browser and FastAPI backend within the same execution namespace. Browser web security and site isolation were enabled; flags disabling those boundaries and single-process mode were removed. The main published page ran with CPU throttling 4x, 150 ms network latency, 750/250 Kbit download/upload and cache disabled. Separate page requests and the editor dashboard used distinct browser pages; the dashboard used a separate authenticated editor context.

Actual published controls created a visitor account, signed in and updated the member-session widget. The visitor cookie was HttpOnly and SameSite Strict. It had Secure=false on the observed HTTP loopback service; HTTPS cookie behavior is implemented but not credited as an observed deployment. Anonymous protected navigation returned 401, wrong-group navigation 403, and the allowed group received the private content with private,no-store. An editor group change revoked the session; reload showed the widget signed out. Signing in again restored access; Sign out denied the private route. Visitor credentials/cookies could not read /api/state.

Before consent, the server had no events and the page had no assignment. The first Allow analytics click produced an actual weighted assignment and one exposure with zero converters. The authored Purchase goal button then collected one conversion and a conversion rate of 1. A separate editor context opened Studio, Visitors & insights, Consented events & experiments and refreshed the real dashboard; it displayed those collected metrics. Decline analytics erased events and assignments; clicking the goal again did not collect another event, and dashboard refresh showed empty events and zero exposures/converters.

The runtime emitted no page errors. Canonical evidence is research/provider-browser/observations-final.json, with recorded dashboard responses and non-secret cookie attributes. Screenshots are research/provider-browser/publication.png and dashboard.png. This run verifies top-level published membership and analytics, not opaque preview continuity, cross-site deployment or real vendor account completion. The separate owner-aware publication route/asset audit is [PRIVATE_PUBLICATION_AUDIT_v0.2.0.md](PRIVATE_PUBLICATION_AUDIT_v0.2.0.md).

## Sandboxed data and commerce widgets

A second independent browser run passed 17 checks in an opaque compiled-preview iframe with browser security enabled and CPU/network/cache conditions as above. The frame reported origin null and parent document access raised SecurityError. Actual backend calls used a local source and Shopify GraphQL protocol fixture; these are transport/runtime observations, not real provider account acceptance.

The fetch widget rendered the allowlisted author.name field from the real server proxy. The product widget exposed three variants: Blue selected initially, Red labeled sold out and disabled, Green with unknown quantity still available for sale. Selecting Green updated its price to 12.00 USD. Adding Green quantity 1 and Blue quantity 2 updated the actual cart count to 3; Clear cart reset it to 0. Checkout then rechecked availability and created the selected Blue quantity 1 cart through the actual backend mutation. The iframe navigated to the returned HTTPS checkout URL, which the browser fulfilled locally as a protocol fixture; the backend checkout remained pending and no payment occurred.

Runtime requests carried the preview nonce without editor authorization or cookies. Provider credentials appeared only in the server-to-fixture transport, and were absent from the editable native document. There were no runtime page errors. Evidence is research/provider-widgets/observations-final.json. Real Shopify token permissions, merchant checkout and payment settlement remain explicitly unverified.
